# Deferred Questions

以下问题在设计过程中被识别，但不需要在实现前回答。标有 ⏳ 的表示需要在开发中调研，标有 🔮 的表示未来可能需重新审视。

## 待调研

### WHU API 边界行为 ⏳

- `GetMeterDayValue` 传入无数据的日期（如安装电表之前的日期）返回什么？空数组还是错误？
- `GetReserve` 的并发安全性——短时间连续调用是否会导致返回值不同？
- WHU API 在凌晨是否可能不可用（系统维护窗口）？

### SQLite 限制 ⏳

- SQLite 默认不支持并发写入。定时任务写入时碰到用户查询，是否会导致查询阻塞？
- SQLite 在 WAL 模式下能否满足查询不阻塞写入？需要验证。

### 订阅回填性能 ⏳

- 一个使用 4 年的房间需要回溯约 1460 天。假设每次 API 调用 200ms + 500ms delay，总计约 17 分钟。是否需要在订阅时异步返回？
- `GetMeterDayValue` 是否支持日期区间查询（代码中只传单日，但接口注释是 startDate/endDate）？如果支持区间，可以大幅减少请求次数。

## 未来决策

### 数据归档 🔮

- SQLite 会持续增长。一年后，1000 个房间 × 365 天 = 365k 条记录，是否仍可接受？
- 是否需要按学年归档历史数据？

### 鉴权扩展 🔮

- 初期不实现 API 鉴权。未来如果 QQ 机器人分开部署，是否需要 API Key 或 JWT？
- 是否要区分管理员权限（查看所有房间 vs 仅自己的房间）？

### 多实例部署 🔮

- 如果需要水平扩展，SQLite 的单文件特性会成为瓶颈。是否需要迁移到 PostgreSQL？
- 定时任务是否允许同时运行多个实例？需要加分布式锁吗？

### 用户订阅管理 🔮

- 当前订阅是房间级匿名订阅。未来如果引入用户身份，是否需要支持"取消订阅"？
- 是否需要记录谁订阅了哪些房间（用于 QQ bot 回复消息路由）？
